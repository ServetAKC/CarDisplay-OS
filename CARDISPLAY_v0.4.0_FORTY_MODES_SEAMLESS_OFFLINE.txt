Car Display OS v0.4.0 - forty visualizers, one green-cyan palette, and an
offline mode that no longer needs a double power cycle.

-------------------------------------------------------------------------------
1. The boot no longer dead-ends
-------------------------------------------------------------------------------

The bug, in the words it was reported in: "if you do not unplug and replug it
twice it searches for Wi-Fi forever, and I have to do it twice to get the setup
page open".

That was exactly what the code did. SpotifyDiyThing.ino's waitForWiFi() ran

    while (!connected) { WiFi.reconnect(); wait 5 s; }

with no exit and, worse, without calling checkForInput() anywhere inside it. So
a normal boot with no reachable hotspot left the connecting animation on screen
with touch never sampled: the OFFLINE VISUALIZER button could not be reached
because the screen that carries it was never drawn, and the setup portal only
opened when detectQuickPowerCycle() forced it. The double power cycle was not a
shortcut to the portal, it was the only route to it.

v0.4:

  - waitForWiFi() gives the saved network a bounded window (OFFLINE_FALLBACK_MS,
    12 s - two retry rounds) and then opens the setup portal on its own. That
    screen is also the one with the OFFLINE VISUALIZER button, so both
    destinations are reachable about twelve seconds after power-on rather than
    never.
  - setupWiFiManager() re-tries the saved network every 20 s while the portal is
    open (PORTAL_SAVED_RETRY_MS), instead of treating the portal as a terminal
    state. A phone hotspot that comes up while the driver is looking at the
    visualizer is now picked up with no reboot and no second power cycle.
    Skipped entirely on a first-ever boot, where wm.getWiFiIsSaved() is false
    and there is nothing to re-try.
  - The double power cycle still works. It is now a way to skip the twelve
    second wait, not the only way in.

-------------------------------------------------------------------------------
2. One palette, and no dark green anywhere
-------------------------------------------------------------------------------

v0.3.14 gave the retro modes their own Y2K palette. v0.3.17 unified them onto
the player green - but did it by varying BRIGHTNESS, so every mode's low end
landed on a muddy dark green, and so did DIM, DARK and PROGRESS_TRACK in the
player UI.

v0.4 varies HUE instead. theme::vizHue(t) walks neon green (60,235,110) to pure
cyan (0,255,255); every value in between keeps G at 235 or above, so no input
can produce a dark colour. The two genuinely structural steps (VIZ_DEEP,
VIZ_GLOW) are dim CYAN, which is a different hue, not a darker green. DIM, DARK
and PROGRESS_TRACK moved to teal for the same reason.

All 117 colour references in the renderer already went through the theme::VIZ_*
names, so redefining six constants recoloured every existing mode at once. That
is the whole return on the v0.3.16 refactor.

-------------------------------------------------------------------------------
3. Twenty more modes (20 -> 40)
-------------------------------------------------------------------------------

  DOLPHIN         a leaping dolphin arcing over the spectrum, Pioneer style.
                  Jump height and speed come from loudness, it flips to face
                  the way it is travelling, it goes dim below the water line
                  and it throws a splash on entry and exit. The dolphin is
                  sprite art (visualizerModes.cpp) because no arrangement of
                  circles and triangles reads as a dolphin at 40x19.
  SPECTRUM ARC    bars standing on a semicircle instead of a line
  TWIN TOWERS     two segmented level meters with the waveform between them
  WAVE TUNNEL     concentric rings whose radii come from the spectrum
  MIRROR X        the mirrored spectrum turned on its side
  COMET TRAIL     a comet on an ellipse, tail length from loudness
  EQ STAIRS       the spectrum as a solid staircase silhouette
  SONAR SWEEP     rotating sweep line over range rings, contacts per band
  FREQ RIBBON     the spectrum as one continuous filled ribbon
  VOICE PRINT     scrolling spectrogram with a wrapping write head
  HEX PULSE       nested hexagons, one per band
  LED MATRIX      a 16 x 12 dot-matrix panel
  SPIRAL ARM      Archimedean spiral pushed outward by the bands
  BOUNCE BALLS    one ball per band under real gravity
  SCAN LINES      CRT-style lines, width from the waveform
  KALEIDO         one quadrant of spokes mirrored four ways
  NEEDLE GAUGE    an analogue VU movement with a falling peak needle
  PARTICLE JET    particles thrown up from the bottom edge
  WAVE GRID       a perspective grid deformed by the waveform
  CHROMA RINGS    one ring per band, thickness from level

Adding a mode is still one row in VisualizerRenderer::MODES. The static_assert
against MODE_COUNT is what turns a forgotten count into a build error instead of
a null function pointer at runtime.

The new modes live in visualizerModes.cpp rather than growing
visualizerRenderer.cpp past 2500 lines, and the direction tables moved to
visualizerGeometry.h so both files read the same numbers.

-------------------------------------------------------------------------------
4. Mode selection
-------------------------------------------------------------------------------

  - Right half of the overlay = next mode, left half = previous. One-way
    cycling was fine for twenty modes; with forty, overshooting the one you
    wanted cost thirty-nine more taps. The chrome now reads "< 12/40 NAME >",
    which is the only hint that the split exists.
  - The chosen mode is written to NVS four seconds after the last change
    (STYLE_SAVE_DELAY_MS) and on overlay close. Cycling through forty modes is
    a burst of taps and should cost one flash write, not forty. A car unit is
    switched off after every drive; coming back on a different mode each time
    read as a bug.

-------------------------------------------------------------------------------
6. Not in this release
-------------------------------------------------------------------------------

Android Auto. It is not implementable on this hardware at any effort level:
projection needs an H.264 decoder, USB Host or certified 5 GHz Wi-Fi, and a
receiver stack Google does not license to hobby projects. The ESP32-2432S028R
has none of those. Bluetooth was considered as the way to drop the hotspot
requirement and explicitly rejected; there is no BLE code in this build.

Build
-------------------------------------------------------------------------------

  pio run -e cyd2usb

  RAM   30.7%  (100480 / 327680)   +136 bytes over v0.3.17
  Flash 43.1%  (1357369 / 3145728) +11.6 KB over v0.3.17

Twenty modes for 11.6 KB is what sharing the per-mode state buffers buys; each
mode carrying its own would not have fit.
