Car Display OS v0.4.0 - forty visualizers, one green-cyan palette, and an
offline mode that no longer needs a double power cycle.

-------------------------------------------------------------------------------
1. The boot no longer dead-ends
-------------------------------------------------------------------------------

The bug, in the words it was reported in: "if you do not unplug and replug it
twice it searches for Wi-Fi forever, and I have to do it twice to get the setup
page open".

That was exactly what the code did. SpotifyDiyThing.ino's waitForWiFi() ran

    while (!connected) { WiFi.reconnect(); wait 5 s; }

with no exit and, worse, without calling checkForInput() anywhere inside it. So
a normal boot with no reachable hotspot left the connecting animation on screen
with touch never sampled: the OFFLINE VISUALIZER button could not be reached
because the screen that carries it was never drawn, and the setup portal only
opened when detectQuickPowerCycle() forced it. The double power cycle was not a
shortcut to the portal, it was the only route to it.

v0.4:

  - waitForWiFi() gives the saved network a bounded window (OFFLINE_FALLBACK_MS,
    15 s) and then opens the setup portal on its own. That screen is also the
    one with the OFFLINE VISUALIZER button, so both destinations are reachable
    fifteen seconds after power-on rather than never. The deadline is taken
    before the first attempt rather than after it, because counting from after
    it overshoots by a whole retry round and lands nearer twenty seconds.
  - A touch anywhere on the connecting screen cuts the wait short and goes
    straight to setup. The touch task is already running by then - displaySetup()
    starts it before waitForWiFi() is called - but the player hotspot map leaves
    the middle of the screen inert, which is exactly where a driver jabs at a
    screen that is not responding. setTouchConnectingMode() gives that screen
    its own map where every coordinate means "stop waiting".
  - setupWiFiManager() re-tries the saved network every 20 s while the portal is
    open (PORTAL_SAVED_RETRY_MS), instead of treating the portal as a terminal
    state. A phone hotspot that comes up while the driver is looking at the
    visualizer is now picked up with no reboot and no second power cycle.
    Skipped entirely on a first-ever boot, where wm.getWiFiIsSaved() is false
    and there is nothing to re-try.
  - The double power cycle still works. It is now a way to skip the fifteen
    second wait, not the only way in.
-------------------------------------------------------------------------------
1b. "Offline" now actually means offline
-------------------------------------------------------------------------------

It did not before. The offline visualizer was opened from the setup screen, and
the setup screen is the captive portal: the AP kept broadcasting, the DNS
responder kept answering, and wm.process() kept being called every millisecond -
all of it on core 0, which is also where the microphone sampling task is pinned.
The README even advertised this as a feature ("the setup hotspot and web page
stay live behind it").

SpotifyDisplay gained wantsRadioSilence(); CheapYellowDisplay returns true for
exactly one state, wifiSetupMode && visualizer.isOpen(). The portal loop honours
it by calling stopConfigPortal(), softAPdisconnect(), disconnect(true, false) -
which keeps the stored credentials - and WiFi.mode(WIFI_OFF). Closing the
overlay brings the portal back up and resumes the saved-network retries.

The trade is real and worth stating: while the offline visualizer is open a
phone hotspot appearing is NOT picked up, because nothing is listening for it.
Closing the overlay resumes that within a second. Tapping OFFLINE MODE is an
explicit decision to stop looking for a network, so it should behave like one.

WiFiManager holds its web and DNS servers in unique_ptrs and resets them in
shutdownConfigPortal(), so the repeated stop/start this introduces does not leak.

-------------------------------------------------------------------------------
1c. The setup screen was redrawn
-------------------------------------------------------------------------------

It is the screen a driver sees whenever the hotspot is not up, which makes it
the second most looked-at screen in the product, and it was a full-screen
rectangle with four loose labels in it.

  - A header with a title and an accent rule, instead of a border drawn around
    the whole screen framing nothing.
  - One rounded panel grouping the three things that have to be typed into a
    phone - network, password, address - as small teal labels over large bright
    values, because the value is the part read at arm's length.
  - A button that reads as a button: double stroke, a filled cap down the left
    edge, "OFFLINE MODE" over "40 VISUALIZERS - RADIO OFF". The CYD has no hover
    or press state, so the affordance has to be in the drawing. Its rectangle is
    the same one OFFLINE_VISUALIZER_ZONE tests in touchScreen.cpp.
  - An animated SEARCHING... chip top right, repainted on its own rather than
    with the whole screen. The unit really is still retrying behind this screen
    since v0.4.0; a completely static screen made it look like it had given up.

"OFFLINE VISUALIZER" measured ~250 px in font 4 against 252 px of usable button
width, so the label is the short one and the detail moved to the subtitle.

-------------------------------------------------------------------------------
1d. The connecting screen
-------------------------------------------------------------------------------

The screen that is up for the whole fallback window, and the last part of v0.4
still drawn the way v0.3 left it. It never mentioned either of the things this
release made true: that the wait now ends, and that touching the screen ends it
immediately.

  - Same header and accent rule as the setup screen, so the two read as one
    product rather than two.
  - Names the network being joined, once WiFi.begin() has been called and there
    is one to name. Blank before that, which is honest.
  - A bar that DRAINS over the fallback window. Time left, not progress made,
    and what it is counting down to is the setup screen opening.
    startWiFiConnectingAnimation() takes that window as a parameter because only
    the caller knows it; zero means no deadline and no bar, which is the forced
    config case.
  - "TOUCH ANYWHERE TO OPEN SETUP", which is the whole point of the touch map
    added earlier in this release and was previously undiscoverable.

The four cycling dots are gone. The four climbing signal bars are not: they are
the animation this screen has always had, and they say "working on it" better
than the dots did. The dots were a second timer stacked on top of the bars
saying the same thing. With them out of the way the bars move up into the space
they left and sit centred, with the countdown bar and the touch hint below.


-------------------------------------------------------------------------------
2. The visualizer palette, and no dark green in any mode
-------------------------------------------------------------------------------

v0.3.14 gave the retro modes their own Y2K palette. v0.3.17 unified them onto
the player green - but did it by varying BRIGHTNESS, so every mode's low end
landed on a muddy dark green, and so did DIM, DARK and PROGRESS_TRACK in the
player UI.

v0.4 varies HUE instead. theme::vizHue(t) walks neon green (60,235,110) to pure
cyan (0,255,255); every value in between keeps G at 235 or above, so no input
can produce a dark colour. The two genuinely structural steps (VIZ_DEEP,
VIZ_GLOW) are dim CYAN, which is a different hue, not a darker green.

Scope: the VIZ_* ramp ONLY. GREEN, BRIGHT, PRESS, DIM, DARK and PROGRESS_TRACK
keep the exact hex values they have had since v0.3 - the player screen, header,
clock and setup screens are meant to look as they always have.

That separation did not previously exist. VIZ_GLOW, VIZ_MID, VIZ_BRIGHT and
VIZ_PEAK were literally defined as DIM, GREEN, BRIGHT and PRESS, and fourteen
places inside the mode drawing reached for theme::DIM and theme::DARK directly,
so the two palettes could not be retuned independently. Those fourteen now use
VIZ_GLOW and VIZ_DEEP. The three overlay chrome uses - the close button, the
MIC ERROR text and the mode label - stay on the player palette, because they are
UI drawn over the visualizer rather than part of it.

Everything else already went through the theme::VIZ_* names, so redefining six
constants recoloured all forty modes at once. That is the return on the v0.3.16
refactor.

3. Twenty more modes (20 -> 40)
-------------------------------------------------------------------------------

  DOLPHIN         a leaping dolphin arcing over the spectrum, Pioneer style.
                  Jump height and speed come from loudness, it flips to face
                  the way it is travelling, it goes dim below the water line
                  and it throws a splash on entry and exit. The dolphin is
                  sprite art (visualizerModes.cpp) because no arrangement of
                  circles and triangles reads as a dolphin at 40x19.
  SPECTRUM ARC    bars standing on a semicircle instead of a line
  TWIN TOWERS     two segmented level meters with the waveform between them
  WAVE TUNNEL     concentric rings whose radii come from the spectrum
  MIRROR X        the mirrored spectrum turned on its side
  COMET TRAIL     a comet on an ellipse, tail length from loudness
  EQ STAIRS       the spectrum as a solid staircase silhouette
  SONAR SWEEP     rotating sweep line over range rings, contacts per band
  FREQ RIBBON     the spectrum as one continuous filled ribbon
  VOICE PRINT     scrolling spectrogram with a wrapping write head
  HEX PULSE       nested hexagons, one per band
  LED MATRIX      a 16 x 12 dot-matrix panel
  SPIRAL ARM      Archimedean spiral pushed outward by the bands
  BOUNCE BALLS    one ball per band under real gravity
  SCAN LINES      CRT-style lines, width from the waveform
  KALEIDO         one quadrant of spokes mirrored four ways
  NEEDLE GAUGE    an analogue VU movement with a falling peak needle
  PARTICLE JET    particles thrown up from the bottom edge
  WAVE GRID       a perspective grid deformed by the waveform
  CHROMA RINGS    one ring per band, thickness from level

Adding a mode is still one row in VisualizerRenderer::MODES. The static_assert
against MODE_COUNT is what turns a forgotten count into a build error instead of
a null function pointer at runtime.

The new modes live in visualizerModes.cpp rather than growing
visualizerRenderer.cpp past 2500 lines, and the direction tables moved to
visualizerGeometry.h so both files read the same numbers.

-------------------------------------------------------------------------------
4. Mode selection
-------------------------------------------------------------------------------

  - Right half of the overlay = next mode, left half = previous. One-way
    cycling was fine for twenty modes; with forty, overshooting the one you
    wanted cost thirty-nine more taps. The chrome now reads "< 12/40 NAME >",
    which is the only hint that the split exists.
  - The chosen mode is written to NVS four seconds after the last change
    (STYLE_SAVE_DELAY_MS) and on overlay close. Cycling through forty modes is
    a burst of taps and should cost one flash write, not forty. A car unit is
    switched off after every drive; coming back on a different mode each time
    read as a bug.

-------------------------------------------------------------------------------
6. Not in this release
-------------------------------------------------------------------------------

Android Auto. It is not implementable on this hardware at any effort level:
projection needs an H.264 decoder, USB Host or certified 5 GHz Wi-Fi, and a
receiver stack Google does not license to hobby projects. The ESP32-2432S028R
has none of those. Bluetooth was considered as the way to drop the hotspot
requirement and explicitly rejected; there is no BLE code in this build.
